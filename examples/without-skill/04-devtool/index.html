How it works

From a noisy suite to a trusted one in three steps.

Tern sits next to your existing CI. It doesn't run your tests or change how they run. It reads the results and gets smarter with every build.

01

Add the reporter

One step in your CI config uploads JUnit-style results after each run. Tern picks up your frameworks, shards and retries on its own.

02

Tern learns your suite

Tern compares outcomes on the same commit across branches, retries and machines. A test that both passes and fails without a code change gets flagged, usually within a day.

03

Quarantine, then fix

Flaky tests keep running but stop failing builds. Each one gets a diagnosis and an owner, and Tern releases it once it passes 200 runs in a row.

Root-cause diagnosis

“It's flaky” isn't a diagnosis. This is.

Tern correlates failures with timing, run order, worker assignment and environment, then reads the stack trace to point at the line that breaks. Five patterns cause almost every flaky test, and Tern names which one you have.

Races and timing

Async work that resolves in a different order on a busy runner. Tern shows the two calls that compete.

Test-order dependence

A test that only fails when another one runs first. Tern finds the polluting test by bisecting the run order.

Leaked shared state

Globals, singletons, database rows and mocks that outlive the test that created them.

Environment drift

Timezones, locales, CPU count and image versions that differ between runners.

Real network calls

Requests that slipped past your mocks and depend on a service being up.
